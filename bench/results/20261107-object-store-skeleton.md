## What runs end to end

`nata-parquet` gets a seam (`remote.rs`: `RemoteIo`, `RemoteQuery`): the scan asks for a footer and for the byte ranges of one row group and decodes from memory, through the same `CountingRead::at_eof` guard as a file. `nata-objstore` implements it (the only crate that depends on `object_store` 0.14.2, features `aws` and `gcp`): the ADR 0011 policy ported from the spike (attempt caps 16 per query and 32 per node, 4 attempts, equal-jitter backoff, 30 s per attempt, 120 s per read, `Retry-After` inside the deadline, If-Match and version pinning, chunk-by-chunk length checks, cancel at every wait), grants from ADR 0009's `MemoryManager` reserved **before** each request (a unit's total as one grant; a waiting read parks on the service's sticky wake and leaves its queue slot on cancel), range merging inside one row group only, and the ADR 0012 footer cache (key with credential scope and identity, parsed-size charge, 64 MiB / 1,024 / 16 MiB, LRU among unpinned, pinned bytes stay charged, over-cap entries bypassed and held under the query grant). `nata sql` binds a path or glob through `RoutedSource` (LIST for a glob, the footer for the schema), `nata serve` does the same and accepts `s3://` and `gs://` table locations in its registry (ADR 0014's snapshot interface; one object per table), and `nata-check --object-store fake|s3://..|gs://..` runs a query set with DuckDB on the local directory and Nata on the same bytes in the store.

Credentials: environment and instance metadata only. Nothing secret is formatted into an error, a Debug string or a log: errors carry a class and an attempt count (`the store answered with a server error (after 4 attempts)`), never the library's text. Tests plant canary keys, endpoint and body text and fail if they appear (and a planted-leak check proves the check can fail).

## Rule 1 gates

**(a) S3 credential chain.** Rule: "both auth chains ... work behind our wrapper"; part 3 lists "the S3 credential chain". Test `tests/credentials.rs` against the fake endpoint (it answers 403 to any request not signed by the expected access key id, and logs the key id of each request) and a fake IMDSv2: environment keys sign every request; a profile of the shared credentials file supplies static keys (read by us, at most 64 KiB; `object_store` has no profile support), and environment keys win over it; with nothing else configured the instance metadata gives the key (token PUT, role listing, credentials; the session token accompanies every request; credentials are reused, no second metadata call); a wrong key is `access was denied` and the message holds neither key; a dead metadata service ends in a bounded error. **Verdict: MET on the fake.** Not exercised: web identity (https required), ECS/EKS container credentials (fixed or env addresses), refresh near expiry, SigV4 signature correctness (the fake checks WHICH key signed, not the signature; the library's signer is the spike's and the aws crate's), real S3, MinIO. Reproduce: `cargo test -p nata-objstore --test credentials`.

**(b) `cargo deny` and the unsafe inventory.** Rule: "dependency checks (`cargo deny`, unsafe inventory)". `object_store` 0.14.2 with `aws` and `gcp` adds **145 packages** (no locked version changed; the list is in `Cargo.lock`'s diff). `cargo deny check`: advisories ok, bans ok, sources ok, licenses ok **after one exception** in `deny.toml`: `webpki-root-certs` 1.0.11 (the Mozilla root list, via `reqwest` -> `rustls-platform-verifier`) is under CDLA-Permissive-2.0, which the allow-list does not name; `deny.toml` says other licenses are "decided case by case", so this is a decision for the owner, recorded in the file. Unsafe (textual, `scripts/unsafe-inventory.py nata-objstore`, an upper bound that counts features that are off): 114 of the new packages are in the build tree and hold 15,319 `unsafe` keywords, 11,285 of them in `aws-lc-sys` (C crypto bindings), 762 `aws-lc-rs`, 456 `ring`, 359 `crc-fast`, 297 `lock_api`; `object_store` itself has 2, `reqwest` 5, `hyper` 61, `h2` 1; `rustls` forbids it. Workspace packages: 0. Full table: `raw/object-store-skeleton/unsafe-inventory-new-packages.md`. **Verdict: MET, owner decision needed on the license exception.**

**(c) Hostile lengths on library paths that read success bodies.** Rule: "if the library allocates from hostile lengths before our bound, rule 1 fails". Where `object_store` reads a success body whole (`bytes()`, `text()`, `json()`; from the source of 0.14.2) and what bounds it:

|---|---|---|---|

| LIST page XML | `aws/client.rs list_request`, `gcp/client.rs list_request` | yes (a glob) | our connector collects at most 8 MiB, else a decode error: `endless_list_body`, `oversized_list_document` |

## Fault cases and mutants

**Rule (card part 2, fault tolerance):** "ADR 0011: bounded retries for throttling/5xx/transport timeout/truncation; permanent auth/missing/invalid-range errors fail directly; changed identity fails, never partial success. ... Mutants remove attempt/deadline/length bounds or swallow error." The 29 in-process cases, 3 allocation cases and 15 mutants of the spike were **ported, not rewritten**, to the production wrapper (`crates/nata-objstore/cases/`), plus: a grant case (eight concurrent 100 KB reads under a budget for two run two at a time, grants back to zero), six allocation cases (LIST page, three IMDS answers), and two mutants (`no_success_body_bound`, `no_grant`). **30 in-process + 9 allocation + 7 cache cases pass; 17 of 17 mutants CAUGHT, 0 survived, control passes first** (13 wrapper, 4 cache; table in `raw/object-store-skeleton/mutants-sweep.txt`; 4 m 31 s, debug build). The two scan cases of the spike became end-to-end tests over the real engine (compared with the local file, not an Arrow oracle). Reproduce: `cargo test -p nata-objstore` and `cargo run -p nata-objstore --features mutants --bin objstore-sweep -- mutants`.

## Deviations from the ADRs, and findings

1. **Workers block while they wait (ADR 0011: "bounded byte bridge and sticky park/wake").** A CPU worker waits for the I/O runtime on a channel, polling cancel every 10 ms; it never runs a future (no `block_on`), and a cancel returns within one poll. Parking needs the scheduler to hold not-ready tasks. Consequence: the unit window is the worker count, so `nata sql` and `nata scan` raise the workers to 16 for a remote scan (the attempt cap, ADR 0011 amendment 2), 8 vCPU oversubscribed 2x; `nata serve` does **not** (it keeps its admitted worker budget), so a remote scan there has fewer units in flight. First thing to replace.
2. **Success-body bound in the transport (new).** Proposed ADR 0011 amendment: besides the 4 KiB error body, the connector bounds every success body that is not a ranged read to 8 MiB.
3. **Footer.** A cold open of an object larger than 64 KiB costs the tail read **and** a 4-byte read of the first bytes (the local reader's magic check; run in parallel with the tail): one more request than the spike's footer, not one more round trip. The parsed-footer staging grant is `128 x wire + 4 KiB`, the bound the local reader already uses, not the measured 3.8-5.5x (a damaged footer may expand more); the cache charges the real parsed size.
4. **Binder to execution** shares the footer through the cache, not a handle: the first file costs a second identity lookup (HEAD), no second footer GET. With the cache off the footer is read twice.
5. **Cache memory** is capped at 64 MiB by the cache itself and is **not** reserved from the node pool (ADR 0012: reserved before the admissions are divided). An aggregate over objects reads through the same wrapper with its own per-query budget, in addition to the aggregate service's budget.
6. **Redirects.** `object_store` 0.14.2 has no redirect option, so reqwest's default applies (it follows redirects and strips `Authorization` across origins, but would forward `x-amz-security-token`). Not tested; fixing needs our own HTTP service with `Policy::none()`. Open.
7. **No credentials** on S3 ends in 4.5 s with "the request timed out (after 4 attempts)" (the IMDS lookup times out and is retried as a transport failure); GCS says "access was denied" in 0.6 s. Correct but misleading text.
8. **Errors name the URI the user typed**, not an alias; the wrapper never adds the endpoint, a signed URL or a body. Stable object aliases and sanitized counters in EXPLAIN ANALYZE are not built.
9. `serve` registry: one object per table; no glob, no refresh.

## What the rest of slice 11 must do

1. **Parked bridge** (deviation 1): scheduler-held not-ready tasks, an async ahead stage sized by the attempt cap, no oversubscribed workers, `serve` at its admitted budget; loom at bound 3 for the real waiter/grant-gate code (none written yet).
2. **Real stores:** MinIO or real S3 (SigV4, web identity, ECS/EKS, refresh), GCS service-account and ADC files, token refresh past an hour, TLS, a real replace-during-scan; then rule 1 can be decided.
3. **Measure against the frozen ceilings** on both CPUs (cells above), the 0.9x scalability rule, the RSS envelope and FD limits under a fresh VM, concurrent queries and the node-level admission (ADR 0009 and 0012 reservations, deviation 5), a size-adaptive footer prefetch (amendment 4).
4. **Security:** redirects (deviation 6), the seeded-canary tests through refresh and redirect paths, object aliases.
5. **Cache:** single-flight fills (today duplicate misses each fetch), prepared-plan revalidation, a shared handle from binder to scan, credential-scope refresh in the key.
6. **Operability:** EXPLAIN shows the remote scan and cache policy; EXPLAIN ANALYZE reports requests, retries, useful and fetched bytes, peak grants, cache hits/misses/evictions, identity checks; stable object aliases in errors; a replay trace.
7. **Nightly:** add `objstore-transport-fuzz`, `objstore-object-fuzz` and the sweep to `nightly.yml`; run the deep checks on the closing commit (way of working section 2).
8. **Decisions for the owner:** the `webpki-root-certs` license exception; the proposed amendments (success-body bound, workers-as-window, the footer magic read); the card's text still says remote glob/LIST is out of scope while this brief asked for globs: the skeleton supports them (LIST is bounded at 100,000 keys and 8 MiB per page).
