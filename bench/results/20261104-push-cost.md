The protocol (`api.rs`), the batch type, the scheduler (`sched.rs`), the sync shim and the exchange (`ops.rs`) are **not copied**: `spikes/push-cost/src/lib.rs` includes `spikes/operator-trait/src/*.rs` with `#[path]`, so the benchmark always measures the current operator-trait code.

## The question

ADR 0001 says "push costs little": no difference beyond about ±1-5% in the corrected pull-versus-push comparison (`bench/results/20261104-pull-vs-push-corrected.md`, `bench/results/20261104-arm64-run2-benchmarks.md`). That was measured on a **linear** chain with **Arrow** kernels that allocate per batch (about 11 microseconds per 256-row batch), so a per-batch protocol cost of 0.2 microsecond is invisible. The ADR lists three things it does not cover, and this spike asks about each:

1. **Much cheaper kernels** (an `i64` add, add + compare + filter with a selection vector, in cache). Does the per-batch cost of the protocol (a virtual call per operator per batch, the `OpResult` handling, the scheduler's stage loop and queue) become a visible share?
2. **Static dispatch.** How much of that cost is the virtual call itself?
3. **A branching pipeline** (one producer feeding two consumers through an exchange), where batches cross a channel and tasks park and wake.

## Design

### Work (identical in every arm)

Morsels of `batch` rows (1024, 8192, 65536) pass through `len` stages (1, 3, 6) of one kernel kind, are summed into a checksum, and the work is spread over `threads` OS threads (1 and 4) that take morsels from one shared atomic counter. `2^25` rows (33.5 M) per run, so a run is a few tens of milliseconds to a few hundred.

* The **source** adds the morsel number to a fixed pseudo-random template of `batch` rows (one allocation and one cheap pass, the same code in every arm), so each morsel is different and a lost, duplicated or mis-computed morsel changes the checksum.
* **Cheap kernel:** stage `i` computes `v + (3i+1)`: one column in, one out.
* **Medium kernel:** add (dense, over every row, as an Arrow kernel would), compare `(v & 7) != 0`, and produce a selection vector: column 0 is the values, column 1 the selection vector (absent = all rows). The next stage builds its selection from the previous one. With these constants 7/8, 5/8 and 3/8 of the rows survive 1, 3 and 6 stages.
* **Checksum** = wrapping sum and count of the rows that reach the end. A scalar row-by-row reference (`kernels::reference`, no shared code but the template) is computed once per cell, and **every run's checksum is compared with it right after the run, before its time is kept**; a mismatch panics (a fast wrong answer is not a data point).

### Arms of the linear chain (`src/arms.rs`), interleaved A B C A B C

| arm | what it is | what a difference to the next one means |
|---|---|---|
| `control` | hand-fused loop, const-generic chain length, no operators, no per-stage batch, no dispatch, no scheduler | the baseline |
| `control-twin` | the same code again | **noise floor**: the control against itself |
| `static` | the real `Operator` trait, the unfused kernels, `Vec<Box<StageOp>>` (a concrete type: direct, monomorphised calls), a minimal push driver, per-stage output batches reused, no scheduler | `static - control` = what the *unfused operator shape* costs (a materialised batch per stage) |
| `dyn-direct` | the same driver with `Vec<Box<dyn Operator>>` | `dyn-direct - static` = **the virtual call** |
| `dyn` | the real scheduler (`Query::run`), one `Box<dyn Operator>` per stage: the protocol as the engine would use it | `dyn - dyn-direct` = the scheduler's stage loop, its fresh `Batch::default()` per stage and the dropped inputs |
| `static-in-sched` | the real scheduler with the whole chain as **one** operator `Fused<L>` whose stages are concrete and whose intermediate buffers are reused | `static-in-sched - static` = the scheduler's fixed cost per batch; compared with `dyn` it shows how much a per-stage virtual call plus per-stage hand-off costs inside the scheduler |

**Static dispatch and the API (honest note).** The protocol does not allow monomorphised stages *inside* the scheduler: `Pipeline.ops` is `Vec<Arc<dyn OperatorFactory>>` and the task body holds `Vec<Box<dyn Operator>>`. So "static" is shown two ways: a generic driver outside the scheduler (`static`), and the closest the API allows inside it (`static-in-sched`: one virtual call per batch for a whole concrete chain). Making the scheduler generic over the operator types would be a change to `operator-trait`; this spike does not do it (it is not needed to answer the question, and the included files stay unchanged).

The unfused kernel functions are `#[inline(never)]`, so they are the same machine code in every unfused arm: a difference between arms is dispatch and plumbing, not loop code generation. The control has its own fused loops, which is the point of a control. The control gets the *best* fusion the compiler finds (for the cheap kernel the L adds may collapse into one add), so overhead against the control mixes "fusion not done" and "protocol"; the ladder above separates them.

### Branching topology (`src/branch.rs`)

```
producer pipeline (1 task):  morsel source -> stage 0 [-> compact (medium kernel only)] -> exchange sink
consumer pipeline (2 tasks): exchange source -> stage 1 -> stage 2 -> sum sink          3 worker threads
```

* `proto`: the real scheduler and the real `ops::exchange` of operator-trait; tasks park (`Blocked`) and are woken through wakers. Compaction before the exchange follows ADR 0001.
* `hand`: 3 OS threads and a bounded queue (`Mutex` + two `Condvar`s) that calls the same kernels directly. `hand-twin` is the same code again (noise floor). The control of these cells is `hand`.
* Exchange capacity 1 (nearly every push and pop parks or wakes) and 4. Each batch goes to exactly one consumer task. The checksum equals a 3-stage chain over every morsel.

### What is reported per cell

Per arm: median wall **ns per row**; **ns per batch per worker** (`wall x threads / batches`); and the **overhead against the control**, `(arm - control) / control`, computed **round by round** (paired) with the median and quartiles over the rounds, and the same difference in ns per batch per worker. A cell is flagged `NOISY (IQR > difference)` when the interquartile range of the paired overhead is wider than the overhead itself. The final table gives one line per cell (overhead of `static`, `dyn-direct`, `dyn`, `static-in-sched`, and the twin) with `?` on any flagged value. Raw per-round times are in `rounds.csv`.

Also printed: the **fixed cost of one run** (every arm with zero morsels: thread start, scheduler set-up, join), which is part of every timing.

### Quiet or SANITY ONLY

* the 1-minute load average is printed at the start of the run, before any benchmark thread has run, and at the start and end of every cell. If it is `>= 2` at the start, the run says **SANITY ONLY** and no cell may be called quiet.
* The load average includes the benchmark's own threads (4 busy threads push it towards 4), so it cannot detect a neighbour by itself. Each cell therefore also measures the CPU used by *other* processes (and stolen time) as machine busy time from `/proc/stat` minus this process's CPU time, assuming `USER_HZ = 100`. `>= 0.5` core, an unreadable `/proc`, more threads than CPUs, a smoke run, or a harness that failed its self-test also give **SANITY ONLY**. "quiet" is printed only when none of these holds.

### Harness self-test (runs first; the benchmark stops if it fails)

The cheap kernel, 1 stage, 1024 rows per batch (the cell where a per-batch cost is the largest share), at 1 thread and at 4 threads: the arms `control`, `control-twin` and `control+spin{100,400,1600}ns` (the control plus a busy-wait of that many nanoseconds after every batch) are run interleaved exactly like a real cell. The expected difference is the spin **measured on its own on one thread** (it overshoots by about the cost of reading the clock). PASS needs, for every injected arm, `|median measured difference - expected| <= max(25% of expected, 15 ns)` and an interquartile range not wider than the median; and the twin within `max(10% of a control batch, 20 ns)` of zero. So it shows that the harness can see a difference of 100 ns per batch (about 0.3x of a control batch) and of 1.6 microseconds, and sees none between identical arms. If it fails, nothing is evidence (exit code 2 of `gcp-check.sh`).

## Cells

* Linear chain: 2 kernels x 3 chain lengths x 3 batch sizes x 2 thread counts = **36 cells**, 6 arms each (+ 1 discarded warm-up round, 25 measured rounds by default).
* Branching: 2 kernels x 3 batch sizes x 2 exchange capacities = **12 cells**, 3 arms each.
* Fixed cost of one run (1 row per thread count) and the self-test (1 and 4 threads).

## Verification built in (all of it unrun so far)

* `tests/topologies.rs`: one test per topology. **Linear chain:** every arm (and the spin arm) equals the scalar reference for both kernels, lengths 1/3/6, shapes with odd batch sizes (100, 333, 1), batch counts not divisible by the threads, fewer batches than threads. **Zero input** in every arm. **Branching:** every arm equals the reference for both kernels, 5 shapes and capacities 1, 2, 4; plus 10 repetitions of 3000 batches through a capacity-1 exchange for `proto` and `hand`. All under a timeout, so a deadlock fails instead of hanging.
* The check can fail: tests with a deliberately wrong arm (a dropped morsel; a checksum off by one) must panic with `WRONG RESULT`; the checksum is shown to change on a lost morsel, a stage fewer, the wrong kind and a changed constant; the interleaving order is asserted (`A B C | B C A | C A B | ...`).
* Unit tests of the quartiles, the NOISY rule, the paired overhead, the `/proc` parsing, the quiet/SANITY ONLY rule, and the self-test's pass/fail judgement on synthetic data (accepts the right size, rejects zero, rejects 3x, rejects a noisy series).
* A smoke test runs the whole report path on a tiny grid.

```bash

```

It builds in release, runs the unit tests (release profile, overflow checks on), a smoke pass, waits for the load to settle below 1.0, then runs the self-test and the benchmark. Exit status: `0` ok; `1` build or unit-test or smoke failure (no benchmark run); `2` harness self-test failed; `3` the benchmark failed (wrong checksum in some arm, crash, timeout). Output files in `/path/to/out`: `machine.txt`, `build.txt`, `unit-tests.txt`, `smoke.txt`, **`results.md`**, **`rounds.csv`**, `bench-stderr.txt`, `SUMMARY.txt`.

## How to read `results.md`

1. **Header:** load average at start, CPUs visible. `SANITY ONLY` anywhere in the header means do not quote any number.
2. **Harness self-test:** all rows must say PASS.
3. **Fixed cost of one run** (microseconds): what thread start and scheduler set-up add to every run; compare with the run lengths.
4. **Per cell:** the status line (load, other-process CPU, quiet or SANITY ONLY), the checksum, and the table. Read the *difference in ns per batch per worker* first: it is the cost of the protocol part in absolute terms and does not depend on how cheap the control is. The percentage is large for a cheap control and says little on its own.
5. **Decomposition,** within a cell: `static - control` (unfused shape), `dyn-direct - static` (virtual call), `dyn - dyn-direct` (scheduler stage loop and per-stage batches), `static-in-sched - static` (scheduler fixed cost per batch).
6. **Summary table:** one line per cell. A value with `?` is not a result. If the twin column is itself large, the cell is noisy and its row says nothing.
7. **Branching cells:** `proto` against `hand`; capacity 1 is the park/wake stress case.

**What would count as "push cost is visible"** (stated before the data, to avoid choosing afterwards): a `dyn` or `static-in-sched` overhead that is *not* flagged `?`, is larger than the twin's spread, repeats on both architectures, and exceeds about 5% of the control in a cell. What matters for the ADR is the absolute cost per batch against the cost per batch of a real (Arrow) kernel; a protocol cost of `c` ns per batch is a share `c / (kernel ns per batch)` of the work, so 100 ns per batch is 1% of a 10-microsecond batch and 30% of a 330-ns batch.

## Limits (known before the first run)

* **Nothing here has been run.** Not checked without running: that the tests pass; that the self-test tolerances are met on a real machine; the run times; that the 65536-row cells are not dominated by allocator behaviour (a 512 KB `Vec` per batch may come from `mmap` and page-fault; the control allocates one per batch too, `dyn` allocates one per stage per batch, so the allocator can show up as protocol cost: compare ns/row at 65536 and 8192 rows in the control before trusting that cell); what LLVM does to the control and the fused loops on each architecture (inspect with `perf` or `cargo asm` before explaining a number); how much the SMT siblings of `c3d` change the 4-thread cells.
* The batch type of the prototype is `Vec<Vec<i64>>` with a hand-made selection-vector column. It is not an Arrow `RecordBatch`, and its per-batch outer allocation is part of every protocol arm and not of the control. The real engine's batch (ADR 0003) will differ.
* One scheduler (the prototype's single FIFO queue under one lock, one task per thread); no work stealing, no blocked sources except in the branching cells.
* The `dyn` arm's per-stage fresh `Batch::default()` is the prototype scheduler's choice, not a law of the protocol; a scheduler that kept per-stage output buffers would shrink `dyn - dyn-direct`.
* Wall time per row at 4 threads includes the tail (the last morsels); the shared counter hands out morsels dynamically, so it is small but not zero. Thread start is in every timing (see the fixed-cost table).
* Compile settings: release, `opt-level 3`, thin LTO, `codegen-units 1`, `overflow-checks = true` (the product configuration, ADR 0003 decision 6), baseline target features (no `-C target-cpu=native`).
* `USER_HZ = 100` is assumed for the other-process CPU estimate.
