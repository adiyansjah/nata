# Why does the scheduler cost more with four threads on the x86-64 VM? A pinning experiment (2026-11-05)

**Question.** `20261105-timing-settled-rerun.md` found that with four threads on `c3d-highcpu-8` the real scheduler of `spikes/operator-trait` costs far more than the plain version at large batches (`dyn` minus `static` for one cheap
stage: 65 / 47 / 48 percentage points at 1,024 / 8,192 / 65,536 rows) while on ARM64 it shrinks to 23 / 7 / 3. The cause was open; two candidates were named: the `c3d` has two hardware threads per core, and cross-thread wake-ups.
**Method.** `spikes/push-cost/pin-check.sh` (job `pushpin`) runs the same cells (cheap kernel, one stage, four threads, 25 rounds) three ways with `taskset`, with the CPU sets computed from `lscpu -p` and tested against topology fixtures:
`unpinned` (the OS decides), `distinct` (four threads on four different physical cores: CPUs 0,1,2,3) and `siblings` (four threads on both hardware threads of two cores: CPUs 0,4,1,5). It settles before each run.

**Runs.** `c3d-highcpu-8` (AMD EPYC 9B14, 4 cores x 2 threads, kernel 6.1.0-54) twice (`pushpin-x86`, `pushpin-x86-r2`), `n4a-highcpu-8` (Neoverse-N3, 8 cores x 1 thread) once as the control (`pushpin-arm64-r2`; a first attempt died in the common setup on a transient 504 from
GitHub while downloading DuckDB, $0.001, and that download now retries). 188 to 207 s of VM time each, **$0.004 to $0.005 each**, resources left after cleanup: none. Start loads 0.40 to 0.49 (the sibling re-run: 0.76, SANITY ONLY).

`dyn` minus `static`, percentage points over the hand-fused control (the same two columns the earlier records used):

| machine | pin set | 1,024 rows | 8,192 rows | 65,536 rows |
|---|---|---:|---:|---:|
| c3d, run 1 | unpinned | 65.2 | 50.8 | 49.5 |
| c3d, run 1 | distinct cores | 25.3 | 7.6 | 4.2 |
| c3d, run 1 | sibling threads | harness self-test FAILED, no numbers | | |
| c3d, run 2 | unpinned | 65.4 | 48.7 | 48.5 |
| c3d, run 2 | distinct cores | 24.4 | 6.1 | 4.4 |
| c3d, run 2 | sibling threads, **UNVALIDATED** (self-test failed; start load 0.76, SANITY ONLY) | 28.7 | 5.8 | 0.7 |
| n4a (control) | unpinned | 33.4 | 7.1 | 3.1 |
| n4a (control) | distinct cores | 29.9 | 4.5 | 2.8 |

For reference, the earlier full-grid records: c3d unpinned 65 / 47 / 48, n4a unpinned 23 / 7 / 3.

**What it shows.**
1. **The extra cost is reproducible on the `c3d` and is a thread-placement effect.** Unpinned it is 65 / 49 / 49 points in both runs (and in the earlier record). With each worker kept on its own CPU it falls to 25 / 7 / 4, the ARM64 level, in both runs.
2. **It is NOT caused by two threads sharing a core.** The sibling run (four threads on two cores) shows the same collapse (29 / 6 / 1) as the distinct-core run, while sharing a core is exactly what it does. That run is unvalidated (below), so the claim rests on direction, not on magnitude.
3. **The ARM64 control hardly cares about pinning** (33 / 7 / 3 against 30 / 5 / 3): the cost there was already small.
4. **The arm without the scheduler is unaffected by pinning:** `static` at 8,192 rows reads +47% unpinned and +49% / +58% pinned on the `c3d`, so the effect belongs to the path that wakes and migrates worker threads (the one global `Mutex<VecDeque>` run queue and a `Condvar`, `notify_one` per wake), not to the kernels.
5. **The harness refused to validate the sibling run:** an injected 100 ns busy-wait read as +190 to +202 ns against a tolerance of about 33. Two threads sharing a core slow each other's spin loops, so a measurement that injects spin delays cannot be trusted there. The numbers of that run are labelled UNVALIDATED in the script's table and must not be quoted as evidence.

**Correction to what was written earlier.** The settled-rerun record and the note in ADR 0001 named "two hardware threads per core" as a candidate. This experiment does not support it: sharing a core does not reproduce the cost, keeping the workers in place removes it.

**What it does not show.** The mechanism: why moving workers costs so much on this VM and so little on the Neoverse VM (candidates, all untested: the kernel placing a woken worker on another CPU with cold caches, the cost of waking an idle virtual CPU, the futex path). Whether the real CPU pool of ADR 0002 (`crossbeam-deque` work stealing, not this single-queue prototype) shows the effect, and whether pinning workers or sticky scheduling is the right mitigation. One VM type per architecture; no other x86-64 VM type; the quiet Intel desktop probe (21 / 8 / 22, unpinned) is consistent with a
machine that does not show it, not with a cause.
