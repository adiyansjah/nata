## Correction, 2026-11-04 (read this first)

The first version of this file reported "25 of 25 unit tests pass" and "60 of 60 mutants caught", and a NULL penalty of "1.0-1.15x". Re-verification found `the_word_wise_engine_matches_a_scalar_reference_for_every_step_density_and_overflow` **failing in the release profile** (3 of 3 runs; passing in the debug profile), with the non-NULL count of the first SUM column wrong (`nn: [177, 177, 165]` against the reference `[186, 177, 165]`, sums and counts equal). What I found:

- **Root cause: not an engine defect. A stale test binary was reused.** `mutate.py` ran every mutant in a private copy of the source but compiled it into the *same* `target/` directory as the real project. Cargo names the artifacts of a workspace member without using the source path, so after the last mutant (`engine: non-NULL count of a group wrong`, which computes column 0's count from column 1's NULL counter) the real tree's next `cargo test --release` considered its test binary up to date and ran the **mutant's** binary. The failing test was doing its job: it caught the mutant. Debug passed because the mutation harness only ever builds `--release`, so `target/debug` was never touched. The pattern in the failure fits exactly: the engine's `nn[0]` equalled `nn[1]` in all six groups (a count computed from the wrong column).
- **Evidence, with the source unchanged** (md5 of `src/wengine.rs` identical before and after): (1) `cargo test --release the_word_wise` in the real tree: pass. (2) Run only that one mutant with the old harness. (3) The same command in the real tree again: fails with the same panic text, `nn: [177, 177, 165]` for group ("A","F"). A fresh `cargo clean -p spike-null-path --release` followed by the same test: pass. 150 runs of a passing binary under different environment sizes, 4 values of `MALLOC_PERTURB_` and 3 CPU pinnings: all pass, so there is no run-time nondeterminism either. Searching for a smaller failing input in the real code found none (every single batch of 1..130 rows, all 63 subsets of the six batch sizes, 12 seeds, 5% NULLs, steps 1/2/3a/3/6: all equal to the reference); there is nothing to shrink because the code under test was right.
- **Fix:** `mutate.py` now uses its own target directory (`target/mutate-target`, seeded with a copy of the compiled dependencies) and refuses to start if it would share the real one. The contaminated artifacts were removed (`cargo clean -p spike-null-path --release`) and everything below was rebuilt and re-run on the clean tree.
- **What the incident did show: gaps in my tests**, now closed. (a) The engine property test used `Decimal64Array::from(Vec<Option<i64>>)`, which stores **0 under every NULL slot**, so a kernel that let NULL slots into a sum would not change a sum (the failure above had equal sums); values under NULL slots are now non-zero and sometimes huge. (b) Densities 1, 3, 5, 25, 75 and 95% were not covered by `nullcheck` or by the property test; both now cover them. (c) `nullcheck` ran only 8,192-row batches; it now also runs 1,000- and 97-row batches (partial last words in every batch).
- **Claims withdrawn or changed** after the clean re-run: "25/25" is now 26/26 in both profiles; "60/60" is now the number in the mutation section (62 mutants, isolated target); the timing conclusions that I drew from loaded runs are replaced by the near-quiet run below; in particular the claim that the "subtract NULL rows" sink design cut the sink's NULL overhead from 66% to 9-17% is **withdrawn** (it compared stage tables taken at different loads and not interleaved; in the interleaved near-quiet ladder the per-row-mask design has the *lower penalty ratio* and the subtract design the *lower absolute time*, see step 3), and "wrapping sink adds gain about 3%" is **withdrawn** (they were slower in both near-quiet runs).

## Result in one paragraph

Engine only, batches in memory, CPU-time clock, near-quiet machine (load average 1.8-2.0, sanity only): the NULL penalty at 10% NULLs in four columns (time with NULLs divided by time without NULLs, same arm, paired per round) went from **2.3-2.4x (old engine) to 1.08-1.22x** for Q1 and **2.2-3.0x to 1.0-1.12x** for Q6, at 1 and 4 threads (steps 5 and 6; tables below). The target was at most 1.3x. At 50% NULLs Q1 is at 1.23-1.34x (the cost of the design grows with the NULL count: each NULL row is corrected individually). Against the *old engine without NULLs* the word-wise engine with 10% NULLs took 0.82-0.88x on Q1 and 1.13-1.17x on Q6 (the new engine's own no-NULL Q6 is 1.07-1.16x the old one, a cost of the bitmap bookkeeping that the ratio hides). The quartiles are narrow in this run (a few percent) but it is one run on a shared machine at a load of about 2; the confirmation on a quiet VM (x86-64 and ARM64) is still to be done.

## What was built

`spikes/null-path/src/`:

- `bits.rs`: validity and selections as `u64` words (bit `j` of word `w` is row `64w+j`, tail bits zero), `read_word` (works for sliced Arrow buffers with a bit offset), `Sel` = `All | Mask(words) | Idx(row indexes)`, `mask_to_idx` (branch-free compress for dense words, `trailing_zeros` loop for sparse ones).
- `wk.rs`: the word-wise kernels `filter_range`, `sub_const_left`, `mul`, `sum`, `group_sums`, each with a dense form (64 rows per step) and a sparse form (selected rows only, one validity bit per row).
- `wengine.rs`: the same Q1/Q6 pipeline as `generic-ops/engine.rs` over `Sel` and validity words, with `Opts` flags so each step can be switched on separately (the "ladder").
- `kernels.rs`, `engine.rs`, `fused.rs`, `nulls.rs`, `source.rs` (plus a `with_batch_rows` setter): from `generic-ops` (control arm, hand-fused baseline, NULL injection and the independent scalar reference).
- `main.rs`: modes `check`, `nullcheck`, `ladder`, `density`, `stages`, `wloop` (and the old `bench`, `membench`, `nullbench`).
- `mutate.py`, `run-all.sh`.

Rules kept from ADR 0003 decision 4: an overflow is an error only for a row that is selected **and** valid; a NULL input gives a NULL output; a NULL in a filter column drops the row. Built and tested with `[profile.release] overflow-checks = true` (decision 6).

## What was tried, in order, and what the evidence says

Timing evidence is sanity only. All numbers in this section are from the interleaved ladder of the table "Ladder" below (CPU clock, load average 1.94 at the start and 1.84 at the end, 9 rounds + warm-up) unless stated. "Penalty" = time with 10% NULLs / time without, same arm, paired per round.

1. **Validity as bitmaps, predicate bitmask ANDed with the validity word per 64 rows, selection vector built from the mask (task steps 1+2, "step 1").** The per-row `valid.ok(i)` test, the per-batch byte expansion of four validity bitmaps and the hybrid are gone. Penalty Q1 1 thread 2.35 to 1.56, Q6 1 thread 2.61 to 1.11; the absolute time with 10% NULLs is 0.77 (Q1) and 0.42 (Q6) of the old engine's. **Helped most of the gap on its own.** Cost: with no NULLs it was 1.12x (Q1) and 1.15x (Q6) the old engine's time (the first version converted bitmaps to indexes with a `trailing_zeros` loop; the adaptive `mask_to_idx` is in all rows here).
2. **Word-wise Project (dense selections as a bitmap; one AND per word of the operand validities; error flag `(overflow_bits & valid_word & selected_word) != 0` per word) ("step 2").** Q1 1 thread 1.56 to 1.33, 4 threads 1.39 to 1.29; Q6 unchanged (1.11 to 1.12). **Helped on Q1.** (An earlier loaded run could not separate this step from noise; this one can.)
3. **Word-wise sinks ("step 3").** Two designs, both exact and both tested:
   - **3a, per-row masks:** per row, the validity bit of each of the three SUM columns becomes a mask and NULL counters are updated per row. Q1 1 thread: 82.4 ms without NULLs, 81.9 ms with 10% (penalty **1.00**); 4 threads penalty 1.02.
   - **3, add every selected row as if there were no NULLs, then subtract the selected NULL rows through the set bits of `selected & !valid` and count them there:** Q1 1 thread: 68.3 ms without NULLs, 77.7 ms with 10% (penalty **1.13**); 4 threads 1.10.
   So 3a has the *lower ratio* and 3 the *lower absolute times* (17% faster without NULLs, 5% with 10% NULLs): 3a's loop does the mask and counter work for every row even when no column has NULLs, which inflates its denominator. Reasoned (a guess): 3 pays per NULL row, which is why its penalty grows with the density (Q1 1.23-1.34 at 50% NULLs). Neither is clearly the winner on the ratio; 3 is kept as the base of the later steps because it is faster in absolute terms and has the no-NULL fast path. Both are in the binary (`Opts::STEP3A`, `Opts::STEP3`) and in the tests.
4. **Null-rejecting filters ("step 4"):** a filter on column c drops its NULL rows, so c is valid for every later operator (Q6: `l_discount` in the multiplication). Q1 1 thread absolute time with 10% NULLs 77.7 to 73.0 ms (6%); Q6 unchanged within the noise. **Small gain on Q1, none on Q6**; kept because it is exact (engine test, focused test, mutants).
5. **Deferred overflow flag ("step 5"):** the dense Project loop only ORs the overflow flag of each row (no per-row bit packing); validity and selection are consulted only for a word where some flag was set (exact, rare). Q1 1 thread: 63.8 to 48.1 ms without NULLs, 73.0 to 55.3 ms with 10% (-25%). **The largest single absolute gain after step 1**; the penalty ratio does not fall (1.12 to 1.16) because the no-NULL denominator shrinks as well.
6. **Wrapping accumulations in the sink ("step 6"):** the `i128` sums and `u64` counters use `wrapping_add` (they cannot overflow: fewer than 2^64 addends of at most 2^63 each stay below 2^127; counts are bounded by the number of rows) instead of the checked `+` that `overflow-checks = true` turns into a `jo` after each accumulation. **Did not help; slightly slower in both near-quiet runs:** Q1 1 thread 48.1 to 54.0 ms (no NULLs) and 55.3 to 60.5 ms (10%) in the ladder; 48.5 vs 53.5 and 56.3 vs 59.1 ms in the density run; 4 threads 71.6 to 77.8 and 83.1 to 87.5 ms. A guess, not examined: a different register allocation of the sink loop. **Step 5 is the recommended configuration; step 6 is kept in the code only so that the comparison can be repeated** (it also needs the "cannot overflow" argument, which step 5 does not).
7. **Density threshold for keeping a bitmap (`dense_div`) 8 to 4, and adaptive `mask_to_idx`:** Q6's first filter keeps about 15% of the rows, above 1/8, so the second filter evaluated its predicate on all 8,192 rows per batch. `NATA_DENSE_DIV=4/8/16`, Q6 stage totals at 1 thread (loaded, min of 10 passes, not interleaved across settings, so weak evidence): 45.2 / 53.3 / 51.0 ms. Set to 4 (the old hybrid's threshold; **tuned on these two queries only**). `DENSE_WORD = 16` in `mask_to_idx` is untuned.
8. **Compiler check (static, `objdump`, binary of the loaded session):** the date/decimal predicate-to-bitmask loop is scalar (`setge`/`setle`, `shl`, `or`; no `pmovmskb`); the Project loop has `seto` after each `imul` (scalar 64-bit multiply overflow; SSE2 has no 64-bit multiply); the sink function has `bt` for bit extraction, `adc`/`sbb` for the `i128` adds and no vector instructions in the accumulation (the group-indexed read-modify-write cannot vectorise); 20 `jo` in the sink function come from the checked variants that are kept for the comparison. A guess from these counts: the remaining floor of Q1 is the group-indexed read-modify-write of about ten accumulators per row, the same with and without NULLs.

Things not done: SIMD intrinsics for the predicate bitmask (`pmovmskb` / NEON equivalent; per-architecture code), `-C target-cpu=native` runs, packing the count and NULL counters into lanes of one `u64` per group (untried), a register accumulator for few groups (untried; Q1's four groups are interleaved randomly in the data), buffer pooling (the new engine's no-NULL Q6 is 1.07-1.16x the old one; allocation per batch is the first suspect, not checked).

## Mutation check

`spikes/null-path/mutate.py` copies the project to a private directory **with a target directory of its own** (the fix of the incident above), applies one deliberate breakage at a time to `wk.rs`, `bits.rs` or `wengine.rs`, runs the unit tests (and, for a mutant that survives them, `check` and `nullcheck` end to end), and restores the file. Machine-independent. Result on the final tree: **62 mutants, 62 caught by the unit tests, 0 caught only end to end, 0 survived, 0 stale** (about 1 h through the shared-machine lock). The 62 are the 60 of the first version plus two that reintroduce the defect class of the incident (a NULL counter incremented for the next column, in the index-selection kernel and in the per-row-mask kernel); the first version's "non-NULL count of a group wrong" (the mutant that caused the incident, via the stale binary) is #62.

History, so that the numbers can be traced: the first run of the first version had 2 survivors out of 60 (both behaviourally equivalent: they change the representation, not a result) and 1 mutant that did not compile; a test of the options (`the_options_decide_the_representation_and_what_is_known_valid`) killed the two, the third was rewritten; that version of the harness shared its target directory with the real tree (the incident). **The three counter mutants (#48, #49, #62) are each killed by the focused test alone**: `MUTATE_TEST=non_null_counts_are_per_column python3 mutate.py <file> "non-NULL count" "NULL counter"` runs only that test and reports 3 of 3 caught (before the test selected an index vector in step 1, one of them survived with it; the test now includes a filtered-out row for that reason).

## Cost of `overflow-checks`

- **Not measured cleanly** (the A/B needs a quiet machine). `Cargo.toml` has a `nochecks` profile (same as release, `overflow-checks = false`); `run-all.sh` section 3c alternates the two binaries A B A B on the GCP VM.
- What exists: (a) the earlier ARM64 measurement on the old engine: the generic engine 3-5% slower with the checks on (`20261104-arm64-verify-run.md`); (b) in this spike the one place where checked arithmetic sits in a per-row loop is the sink's accumulation; removing those checks (step 6, wrapping adds) did **not** make it faster in two near-quiet runs (step 6 was 5-12% slower than step 5 at 0% and 10% NULLs, Q1), so on this code the checked adds cost nothing measurable and the recommended configuration (step 5) keeps them. The kernels outside the sink use `overflowing_*`, which `overflow-checks` does not touch.
- The engine and all tests above were built with the checks on.

## What limits it

- **Measured (sanity):** after step 3 the remaining Q1 penalty is 0.08-0.17 at 10% NULLs, growing to 0.3 at 50%: it is the per-NULL-row correction in the sink (the other kernels' NULL work is per word). With no NULLs the new engine is faster than the old on Q1 (0.69-0.77) and slower on Q6 (1.07-1.16).
- **Static fact:** the sink's per-row work is read-modify-write on about ten group-indexed accumulators, with `bt` for bit extraction; none of it vectorises.
- **Guess:** the correction loop's cost is a mispredicted loop exit per word and column plus about 12 micro-operations per NULL row.
- **Not known:** whether ARM64 (Neoverse) behaves the same; NULL distributions that are not uniform (runs of NULLs make the correction loop cheaper per row; alternating NULLs dearer); the Q6 no-NULL slowdown.

## Limits

- x86-64 only; one shared VM at a load of about 2; TPC-H SF1 `lineitem`, two query shapes, no joins; synthetic uniform NULLs in four columns (the decimal and date columns that the queries touch; the group key and dictionary columns have none; a NULL group key is still an error as in generic-ops).
- The group-by supports at most 32 distinct values per dictionary key column (`G = 32`, as in generic-ops).
- `Project` before a later filter is not supported by this spike (asserted); filters must precede the projection.
- Buffers (selection masks, output vectors) are allocated per batch; no pooling.

## For the GCP run (nothing was run on GCP; no cost incurred)

`spikes/null-path/run-all.sh <lineitem.parquet> [rounds=25]` does, in order: build both profiles, correctness (unit tests, `check`, `nullcheck`, DuckDB diff), the mutation check (skip with `SKIP_MUTATION=1`; it is not timing-sensitive), then the timing: ladder on the wall clock and on CPU time, the overflow-checks A/B/A/B, the NULL-density table, and the per-stage table for 3a / 3 / 6. It prints `uptime` next to every timing block and warns when the load average is 2 or more. Expected duration on an idle 4-vCPU VM (a reasoned estimate): about 1-1.5 h with the mutation check, 30-45 min without; per architecture. A Spot VM of that size for that long costs a few cents; the human's yes and the cost estimate come first (way-of-working section 8). What the run must settle: (1) the NULL penalty of steps 5 and 6 at 10% (and 50%) on a quiet machine, x86-64 and ARM64, against 1.3x; (2) 3a against 3 and 5 against 6; (3) the A/B cost of `overflow-checks`; (4) why the new engine's no-NULL Q6 is slower than the old one; (5) the NEON/SSE2 behaviour of the predicate loop (is a `pmovmskb`-style kernel worth writing).
