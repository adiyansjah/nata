# Scheduler fairness: starvation reproduced, cooperative time slicing, loom check, overhead (2026-11-04)

Closes the design gap of ADR 0002 (consequence "Fairness is the scheduler's job", open check 2). Code: `spikes/fairness/` (a copy of the bridge spike's scheduler plus the change; `spikes/async-bridge` and `spikes/operator-trait` were not touched). Written by a delegated agent on x86-64 only (8 vCPU shared VM, **load average 13-18 during the measurements and most of the loom runs**, see each section). Nothing here was run on GCP or on ARM64. The orchestrator has not re-run it.

## 1. The failing control (before any change)

Scenario (`tests/starvation.rs`, `src/load.rs`): W pool threads; K CPU-heavy tasks (one pipeline, each ~60 s of work in 1 ms morsels of real CPU spinning); one small task (3 morsels x 1 ms = 3 ms of CPU) started last. The test gives the small task 2 s. Only the scheduler's default API is used (`Query::new(..).start(w)`).

Run on the unmodified scheduler (`spikes/async-bridge/src/sched.rs`, sha256 6dcc6dde...), `--test-threads=1`, load 0.6-0.8 at the time:

```
test control_free_worker_completes ... ok          (W=2, K=1: a free worker exists; small task done in 3.2 ms)
test one_worker_two_heavy    ... FAILED   STARVED: the 3 ms task did not complete within 2 s (workers=1, heavy=2)
test one_worker_four_heavy   ... FAILED   (workers=1, heavy=4)
test two_workers_two_heavy   ... FAILED   (workers=2, heavy=2)
test two_workers_four_heavy  ... FAILED   (workers=2, heavy=4)
test two_workers_eight_heavy ... FAILED   (workers=2, heavy=8)
test result: FAILED. 1 passed; 5 failed
```

So the completion latency is unbounded in the cases where every worker is occupied (it would complete only after a heavy task ends, about 60 s), and the harness itself is fine (the positive control with a free worker completes in 3 ms). After the change the same file passes 6 of 6 (latencies 3-19 ms, below). The old behaviour stays available as `SliceConfig::unlimited()`, and two control tests (`control_unlimited_slice_starves`, `control_consumer_starves_without_slicing`) assert that it still starves, so the tests keep being able to detect the problem.

## 2. Design

**Where a task can be stopped.** `TaskBody::run` loops `advance` (pushes the pending batch through the operators and the sink) and `source.next` (one morsel). Operators and sinks are synchronous and cannot be interrupted, so the only safe cut points are the places where `advance` returns `Flow::NeedSource`: every stage is drained and nothing is half-processed. The old scheduler never returned from `run` except for `Blocked` or `Done`, so a task that never blocks keeps its worker.

**The change** (diff in `SNAPSHOT.md`, about 90 lines in `sched.rs`):

- `SliceConfig { max_morsels, max_time }` (default 32 morsels or 1 ms, whichever first; `unlimited()` for the old behaviour), set with `Query::with_slice`. The time budget is checked only between morsels.
- At each `NeedSource` boundary, if the slice is used up (and at least one morsel ran in it) **and the run queue is not empty**, `run` returns a new `Step::Yield`. If the queue is empty it renews the slice in place (a lone task pays no round trip through the queue; it still waits at most one more slice if a task becomes runnable right after).
- `run_task` handles `Yield` as: lock the state; clear `in_run`; set `Queued` (a pending `notified` is subsumed, the task is runnable anyway); unlock; `enqueue` at the back (`push_back` + `notify_one`). The state machine (`Queued / Running{notified} / Parked / Done`) and `wake` are unchanged: `Yield` is a fourth exit from `Running`, to `Queued`, never to `Parked` or `Done`.
- Also added: a counter of yields (`RunningQuery::yields`, `wait_with_stats`), an assertion (`invariants` feature, on by default, and under loom) that a task is only ever started from `Queued`, and a test-only env hook (`slice-env` feature) that sets the default slice, so the old suites could be re-run with a 1-morsel slice.

**Guarantee (cooperative, at morsel boundaries; reasoned, then tested).** Let S be the longest time a task keeps a worker after starting a slice: `max_morsels x longest morsel`, or `max_time + longest morsel`. With W workers and K other tasks that are always runnable (worst case), FIFO re-queue at the back means a task that becomes runnable starts within `ceil(K / W) x S` (the W running tasks finish their slices within S, then the queued ones are taken W at a time). A task needing m morsels of total CPU c completes within `n x ceil(K / W) x S + c`, with `n = floor(m / max_morsels) + 1` slices (the "+1": end-of-input is discovered by a `next` call that is itself preceded by a slice check). Not covered by it: a single morsel (or a `HaveMoreOutput` loop of one input batch) that is itself long, because the cut points are the source's morsel boundaries; and OS-level descheduling of the pool threads.

## 9. Limits

- **Sanity-only overhead.** Load 13-18; no cost of slicing can be stated; the table above only proves the path is exercised and that results stay correct.
- **Cut points are the source's morsels.** A morsel (or the expansion of one input batch by an operator returning `HaveMoreOutput` many times, a join probe for example) that is itself long is not interrupted; S in the guarantee includes it. A long-running `finalize` or `combine` is not sliced either.
- **Tight timing bound only on a quiet machine**; at load 14 it needs a slack of about 2-3. The wall-bounded spin used for the heavy morsels is a stand-in for CPU work.
- **Loom bounds are small:** 1-2 workers, 1-2 tasks, 1-2 morsels, 1-2 items, preemption bounds 3-5 (one model exhaustive). The time budget and the empty-queue check using a real clock are not modelled (`Instant` is absent under loom); the queue-emptiness check is modelled. Loom does not model SeqCst's total order or spurious condvar wakeups (as in the earlier loom results); x86-64 only.
- **Not covered:** priorities or weights between queries (round robin only, per task, so a query with more tasks gets more of the pool: fairness is per task, not per query); work stealing and per-worker queues (this is the single FIFO queue of the spike, the `crossbeam-deque` design is untested); NUMA; ARM64; the interaction with tokio beyond the channel consumer test; sinks that are `Blocked` mid-slice (covered by the old protocol suites with a 1-morsel slice, not by new models).
- The default slice (32 morsels or 1 ms) was chosen by reasoning, not by data; the overhead run could not choose it.

## 10. Finding (2026-11-04, later): time slicing multiplied the open spill files; fixed in `ops.rs`

Found by the orchestrator on a clean Debian VM (descriptor limit 1024; this machine's is 524288, which hid it): `(ulimit -n 1024; cargo test --release --test protocol finalize_spills -- --test-threads=1)` in `spikes/fairness` failed with `QueryError("spill failed: Too many open files (os error 24)")`; the same test in `spikes/operator-trait` passes. Sections 1-9 above are unchanged; they did not cover this because the copied suites were only run with a high limit.

**(1) Cause, measured.** `ops.rs` kept one `BufWriter<File>` per (task, partition) open from the first spill until `combine`. I added a per-aggregate counter of simultaneously open spill files (`AggStats::peak_open_spill_files`, `spill_file_opens`) and ran `agg_case(200, 256, ...)` (4 scan tasks, 3 workers, 256 partitions, budget 200 groups; `tests/spill_fds.rs`) on the instrumented, unfixed code, load 2.9:

| slice | peak open spill files | opens | outcome at limit 1024 |
|---|--:|--:|---|
| unlimited (old scheduler) | 768 (= 3 workers x 256) | 1,024 | passes |
| default (32 morsels / 1 ms) | 1,020 | 1,024 | fails (peak + stdio and test harness descriptors > 1024) |
| 1 morsel | 1,024 (= 4 tasks x 256) | 1,024 | fails |

Without slicing a task runs to completion, so only the W running tasks hold writers (W x 256); slicing interleaves all T tasks (T x 256). It is also a latent bug without slicing: with `unlimited` and 4 workers the peak is 4 x 256 = 1,024 and the test `spilling_aggregate_under_1024_fd_limit_unlimited_slice_four_workers` fails the same way on the unfixed code. So the descriptor count grew with workers x partitions before, and with tasks x partitions after the slice change.

**(2) Options and cost.**

| option | open files bound | cost | verdict |
|---|---|---|---|
| open-append-close per spill (chosen) | 1 per running worker (3 here), independent of tasks, partitions, slices | more `open`/`close` calls: every spill touches each partition it has rows for. Measured below | smallest change (one function in `ops.rs`; no scheduler, API or `LocalSink` change); also removes the old workers x partitions growth |
| global pool of open files (LRU cap) | the cap | a shared lock on every write, eviction and reopen logic, a new component to test and model | more code, same reopen cost when the working set exceeds the cap |
| close writers when a task yields | W x partitions (not T x partitions) | a new `LocalSink` hook called by the scheduler, flush and reopen of up to 256 files per yield (per millisecond) | still fails with W >= 4 at limit 1024 (the latent case above), and puts file handling in the scheduler's yield path |

Chosen: open-append-close. `spill()` now sorts the drained groups by partition, then for each partition opens its file in append mode, writes one buffer, and closes it in the same call; `combine` no longer flushes writers (nothing is held). Possible later mitigation, not implemented: buffer spilled records per partition in memory up to a small cap before writing, which cuts the opens but takes memory outside the group budget.

**Cost, measured** (paired, alternating, 15 rounds each, load 1.3-1.7; `examples/spill_cost.rs` via `mutants/run_fd_mutant.sh`; one query: 200,000 input rows, 20,000 keys, 4 tasks, 3 workers, 256 partitions, budget 200, default slice; result checked against a reference inside each run): opens 180,912 against 1,024 (177x); wall median 267 ms (min 261) against 125 ms (min 116) for writers kept open, **2.1x slower on this query**. This is close to the worst case for the design (about 200 groups spread over 256 partitions means about one record per file per spill, so each open writes 16 bytes). Larger budgets or fewer partitions write more per open; not measured. Spill is the slow path by definition, but this is a real cost and a number for the ADR, not a free fix.

**(3) Tests (all in `spikes/fairness/tests`).**
- `spill_fds.rs::peak_open_spill_files_by_slice`: peak open spill files <= 3 (the worker count) for unlimited, default and 1-morsel slices. After the fix: 3, 3, 3 (opens 180,912 each).
- `spill_fd_limit.rs` (own test binary, because the limit is process-wide; sets `RLIMIT_NOFILE` soft limit to 1024 inside the test process with `setrlimit`, so it does not depend on the shell): the spilling aggregate with a 1-morsel slice, the default slice, and unlimited with 4 workers. All three fail on the unfixed code with `Too many open files (os error 24)` and pass after the fix (peak 3).
- The orchestrator's command passes after the fix: `test result: ok. 1 passed`.

**(4) Mutant.** `spill_keep_open` (in `mutants/mutate.py`, run by `mutants/run_fd_mutant.sh`) restores one writer per (task, partition) kept open until `combine`. Caught by all five checks: `peak_open_spill_files_by_slice` (peaks 768 / 1,024 / 1,024), the three `spill_fd_limit` tests, and the orchestrator's `ulimit -n 1024` command, each with `Too many open files` or the peak assertion.

**Regression after the fix** (one locked script, load 1.7-2.3): default build, all test binaries pass: fairness 14, protocol 15, shutdown 1, starvation 6, spill_fd_limit 3, spill_fds 1; protocol + shutdown with `NATA_SLICE_MORSELS=1`: 15 + 1 passed; all 16 loom models in one process: 16 passed in 147.9 s (`sched.rs` and `chan.rs` were not touched, and `ops.rs` is not compiled under loom, so the loom result is expected to be unchanged; it was re-run anyway). Not re-run: the mutation table of section 5 (unaffected files) and the overhead table of section 7.

**Limits.** One spilling query shape; the descriptor limit is lowered inside one process on Linux only; the aggregate is the only operator in the spike that spills (hash-join spill, if any, was not checked); the 1,024 figure is the default soft limit of a fresh Debian VM as reported by the orchestrator, not checked here on such a VM.
