## P1: late materialization

**Built** (commit `53e561d`, kept as it was). `RowGroupTask` reads a row group in two steps when the scan has a pushed filter and the option is on (`crates/nata-parquet/src/reader.rs`, `TaskRun::read_late`): step 1 decodes ONLY the filter's columns of the whole row group and evaluates the exact row filter (batch by batch, checking the cancel between batches), which gives a Parquet `RowSelection`; step 2 decodes ONLY the output columns, only for the selected rows (`with_row_selection`). Nothing is read in step 2 when no row passed, and no selection is used when every row passed. Both steps share the task's one counting file handle, so the handle gauge, the byte count, the fault opener and the cancel work as before. A column that is both filtered and selected is decoded twice (the synchronous parquet-rs reader has no predicate cache). The rows, their order and the errors are the default read's. An internal check turns "the rows decoded for the selection are not the rows the filter selected" into an error, never a wrong answer.

**Findings, stated plainly.**
1. `bytes_read` does NOT fall with late materialization: without a page index parquet-rs fetches the whole column chunk of every column it reads, so the only saving is decoding. With the filter column also selected, the late read fetches that chunk twice (functional run: 53.3 MB early, 62.8 MB late on SF1 `l_shipdate`). Whether the decode time saved beats this is what 4b measures.
2. parquet-rs sizes the buffers of a string batch for the batch size, not for the rows selected: a late batch of 200 rows held about 1 MB (`tests/late.rs`), so the memory per result waiting in the reorder window is not smaller by the selectivity. The scan's memory bound is unchanged.
3. A test of the early read changes its expectation only when the late mode is forced (`tests/report.rs`: `bytes_read` of an unpruned scan); the golden `EXPLAIN ANALYZE` file of `nata sql` runs with both variables removed from the child's environment.

**What 4b must measure.** Rule (card part 5): late is kept only if, on SF1 and SF10 and both CPU types, it is at least 1.2x faster than the early read at 10% selectivity and no slower than 1.05x at 100%. The arms are in `scan-bench.sh`, block `late` (it was already in `53e561d`): `nata scan --count --no-prune`, the 7 Q1 columns, 8 threads, window 16; `l_partkey` (not projected: the filter column is decoded in step 1 only) and `l_shipdate` (projected: decoded twice) at 10% (the 10th percentile from DuckDB) and at 100%; arms `early`, `late` and `twin` (early again, the noise control) alternating in every round; the row count of every run is checked against DuckDB's. **Refinement fixed here, before any measurement:** the 10% speed-up is judged on the not-projected column (`pk`), the case P1 exists for; the projected column (`sd`) is reported with its own numbers, and the 100% slowdown bound is judged on both.

## P2: footers read ahead; P10: the binder reads one footer

**Built (P2).** `nata-sched`: `Config::open_ahead = K`. With K = 1 the scheduler is exactly slice 3's (one file opened at a time, only when no task is queued). With K up to K files may be *pending* (being opened by a worker, opened and waiting for an earlier file in `ready`, or queued with unclaimed tasks); an idle worker opens the next file while others run earlier row groups. The results of the openings are installed into the queue **in file order**, a file that cannot be opened is queued in its place as a failure (it takes its sequence number when the workers reach it and stops the claims), so the sequence numbers, the ordered output and the lowest-error rule are those of K = 1. Pending files are bounded by K whatever the number of files (`Summary::max_pending_files`). `ParallelConfig::footers_ahead`, `ExecConfig::footers_ahead`, `--footers-ahead K`, `NATA_FOOTERS_AHEAD`. A worker either runs a row group or reads a footer, so open files stay at one per worker; footers in memory are at most K plus the files whose row groups run (`peak_footers <= threads + K + 1`, tested).

**Built (P10).** `nata-sql::BindOptions { all_footers }`: the default binder reads the footer of the FIRST file only (names and types); `nata sql --bind-all-footers` is the old binder. The scan checks every other file when it reaches it: `ScanOptions::strict_schema` (set by the plan of `nata sql`) requires the same top-level columns, in the same order, with the same types; a file that differs is `ErrorKind::Schema` naming the file ("the files of a pattern must have the same schema (column x ... here, ... in the first file)"), exit code 1, after the rows of the files before it, with the "output is INCOMPLETE" line. `nata scan` keeps slice 3's lighter check (only the columns it reads). `EXPLAIN` no longer reads the later files. Documented in `docs/dialect.md` section 1 and `docs/supported-sql.md`.

**A scheduler fix found on the way** (commit `70210a2`, the earlier agent). In release builds under load, `scan_cli::limit_columns_and_default_columns` failed once ("read=2", expected "read=1"): with a window of 1 the consumer released the slot of the result that satisfied the limit BEFORE it stopped the claims, so a worker could start one more row group in between. The consumer now stops first. Loom model m07 asserts `claimed == 1`; the mutant `stop-after-the-slot-is-released` is caught by it.

**What this step changed in the earlier agent's P2 work.** Its scheduler mutant run had one SURVIVED: `install-does-not-wake-anyone`. After the rewrite of `install` into `finish_open` the end of an opening no longer has to wake the consumer (a failure is queued and the claim path notifies), so only the wake of an idle worker is left, and nothing in the tests needed it: a lost wake costs parallelism, not correctness. A test must therefore make the lost parallelism a hang. **Added: loom model m22 and the std test `a_worker_waiting_for_tasks_is_woken_when_the_opening_of_a_file_ends`**: one file with two tasks that each wait for the other to have started. Re-run: the mutant is now CAUGHT by both (loom: "exceeded maximum number of branches", the spinning task; std: the watchdog).

## R4: page checksums

**What parquet-rs 60.1.0 offers, precisely.** The reader verifies a page's CRC-32 only if the crate is COMPILED with its `crc` feature (`file/serialized_reader.rs:407`: `#[cfg(feature = "crc")] if let Some(expected_crc) = page_header.crc { ... "Page CRC checksum mismatch" }`); there is no reader option. It cannot WRITE checksums (`column/page.rs`: "TODO: Add support for crc checksum", `crc: None`). So: the choice is a cargo feature (`page-crc` of `nata-parquet`, forwarded by `nata`; **on by default**; `--no-default-features` is the build without), the files WITH checksums come from pyarrow (`write_page_checksum=True`), and "verify on versus off" is two builds of the same code, not a flag. **Cost of the dependency:** `crc32fast` 1.5.4 (MIT or Apache-2.0, `cargo deny` ok); `scripts/unsafe-inventory.py` counts 8,121 `unsafe` keywords in the tree of `nata-parquet` against 8,091 before (+30 in 17 files of `crc32fast`, its SIMD paths); the workspace's own crates still have 0. A mismatch is `ErrorKind::Corrupt` ("Page CRC checksum mismatch"), naming the file and the row group, never a value.

**Built.** `crates/nata-parquet/tests/fixtures/` (three small pyarrow-written files with a CRC in every page header, 178 KB together, committed because GitHub's runners have no pyarrow; `make_checksummed.py` regenerates them), `tests/checksums.rs` (5 tests), three checksummed shapes in `tests/fuzz_files.rs`, a CLI test in `scan_cli.rs`, and `crates/nata-bench/checksum-copy.py` (the cost arm's input).
