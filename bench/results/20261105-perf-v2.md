# Where the time goes in Q1 and Q6 on the Neoverse-V2 core (verification-plan item 19)

Date 2026-11-05 (00:46-00:53 UTC). Run `perf-c4a-r2`, job `perf`, one `c4a-highcpu-8` Spot VM (Neoverse-V2, 8 vCPU, Debian 12 arm64), about $0.014. Single thread, batches in memory, TPC-H SF1 `lineitem`,
the generic-operator engine (`spikes/generic-ops`) against its hand-fused loop. `perf record -e cpu-clock` (software clock, a VM has no hardware counters). The timed step waited for a quiet machine first
(load 0.44 after 110 s; the earlier run of the same job at load 2.65 gave the same figures, so the load carried over from the build did not matter for a single-thread run).

## Answer

- **The V2 core does not differ from N3.** Q1 generic over fused is 1.79x here (1.34 s against 0.75 s for 20 iterations); on N3 it was 1.53-1.96x engine only. Q6 is 0.72x (generic is FASTER: 0.33 s against 0.46 s); on N3 0.75-0.77x.
- **Where the Q1 gap is.** In the generic engine 62% of the time is in one kernel, the dense grouped sum (`group_sums_dense`, 3 groups, six aggregates), 22% in the projection pass that materialises the derived columns, 8.5% in the date filter and 2% in the sink. The fused loop spends 91% in a single loop that does all of it per row. There is no time in dispatch, queueing or any virtual-call
  symbol: the gap is the grouped-sum kernel and the intermediate columns, not the operator protocol.
- **Q6 reverses** because the generic engine's filters (40% date filter, 30% decimal filter) shrink the data before the work, while the fused loop evaluates every row.
- Not shown: why the fused Q1 loop is that much cheaper per row (instruction mix, vectorisation); `cpu-clock` sampling cannot say. Hardware counters were not available.
