# 0003: Batch format and expression kernels

Status: accepted (by the owner, 2026-11-05)
Date: 2026-11-03

## Context

Slice 2 builds the batch format and the first expression kernels, and every operator uses them. Requirements:

- No silent coercion; overflow is an error (`vision.md`). Decimals must be exact, and results must not depend on thread count (0001).
- Arrow layout is the interop format and is never replaced (`vision.md`). Dictionary-encoded columns are common in Parquet.
- Reuse a commodity component unless a benchmark shows it is the bottleneck (`vision.md`, `way-of-working.md` section 6).
- Scalar-first, correct and measured on x86-64 and ARM64, runtime dispatch rather than build-time tuning (`portability.md`).

This is open question 3 of `feature-map.md` ("where kernels come from").

## Decision

1. **Batch = Arrow columns plus an optional selection vector.** Columns are Arrow arrays (`arrow-array` types). The selection vector is our own type (arrow-rs has none) and travels with the batch. Compaction (applying the selection) is an explicit step, and happens before a batch enters an exchange (0001) and before any arrow-rs kernel that cannot take a selection.
2. **Dictionary columns stay dictionary arrays in the batch type**, not expanded to strings. Dictionary-aware operator paths (filter, group-by) are the "compressed execution" feature, tier T2 in `feature-map.md`; slice 2 does not require them, but the batch type and kernel interface must not rule them out.
3. **Decimals use the narrowest Arrow type that fits:** `Decimal64` for precision up to 18, `Decimal128` up to 38; above 38 is `not supported yet`. Result precision and scale for arithmetic follow **`docs/decimal-rules.md`**, not arrow's kernels. For multiplication that means DuckDB's width-class cap (two operands of precision up to 18 give a result of at most 18 digits when the scale is below 18), which is also what arrow's `Decimal64` multiply happens to do, so the common case stays 64-bit and every result is checked. Results are widened at the client edge where a protocol needs it: **Flight SQL results are widened to `Decimal128` with the same precision and scale, in both the `FlightInfo` schema and the `DoGet` stream (the Arrow Java library, hence the JDBC driver, rejects `Decimal64`), with the `ARROW:FLIGHT:SQL:PRECISION`, `SCALE` and `TYPE_NAME` field metadata set**; the Postgres wire protocol sends `numeric` and does not depend on the Arrow width.
4. **Errors are raised only for rows that are selected and valid.** `WHERE x <> 0 AND 1 / x > 1` and `CASE` guards must work, so an overflow, invalid cast or division by zero in a row the selection removed, or in a NULL slot, is not an error. Own kernels mask their error flag with selection and validity. arrow-rs wrappers compact their input first (or fold the selection into the validity mask).
5. **Kernels are staged behind our own expression-evaluation interface**, which takes a batch and its selection vector:
   - **Own from the start:** integer and decimal arithmetic (checked, NULL-aware without per-row branches, selection-aware errors), `SUM`/`AVG` and the other numeric aggregates (exact accumulators, `i128` for decimal sums), the hash aggregate and the joins.
   - **arrow-rs behind the interface, with strict wrappers:** comparisons, boolean logic, filter and take, casts (always `safe: false`), string functions and `LIKE`, date and time functions, dictionary operations. Replace one at a time only when a benchmark shows both that the kernel matters (a top self-time entry in a benchmark query, at least 5% of its time) and that a replacement is at least 1.5x faster.
   - **Fused kernels** (for example `a * (1 - b)` in one pass) are an optimization on top of the interface, each with its own bake-off. Expression compilation is T3 (`feature-map.md`).
6. **Strictness is enforced mechanically** (tried; see Evidence): a `clippy.toml` `disallowed-methods` list bans the lenient arrow functions (`add_wrapping`, `sub_wrapping`, `mul_wrapping`, plain `sum`, `cast` and `cast_with_options`); casts go through one `strict_cast` wrapper module that is explicitly allowed to call them with `safe: false`. `overflow-checks = true` is set for release in the WORKSPACE root profile for OUR crates (a per-package setting does not protect inlined or generic kernel code called from another crate; measured, see Evidence) and is switched OFF for dependencies (`[profile.release.package."*"] overflow-checks = false`, and the same for `profile.test` and `profile.dev`): Arrow computes on the slots under NULLs by design and treats their contents as unspecified, so wrapping there is its contract, and with checks on `concat` of dictionary arrays panics (arrow-data 60.1.0 `transform/primitive.rs:46`, `i32::MAX` key under a NULL plus an offset; `bench/results/20261104-hash-ops-correctness.md` section 5, guarded by `spikes/hash-ops/tests/overflow_config.rs`), and the kernel crates also and deny `clippy::arithmetic_side_effects`, `cast_possible_truncation` and `cast_possible_wrap`. `nata-check` carries overflow, invalid-cast and guarded-expression cases.
7. **Every optimized kernel has a scalar reference** and tests against it; fast paths are chosen at runtime and logged (`portability.md`).

## Why

- **Semantics.** Arrow's kernels compute every slot and know nothing about selection, so a strict arrow kernel would raise errors for rows the user filtered out. Owning arithmetic and the aggregates is the way to get selection-aware errors without copying first. Arrow's strict behaviour also exists only behind non-default entry points (plain `sum` wraps, `cast` defaults to NULL), hence the lint.
- **Cost.** Measured on a two-operation expression, arrow's two checked kernels run at about 1.9-2.2 ns/row; two own primitive passes at 1.2-1.3 (1.6-1.8x faster, above the 1.5x rule); one fused pass at 0.77. Arrow's `Decimal128` is the outlier (4.5-9.6 ns/row against 1.3-2.7 for own loops).
- For comparisons, filter, strings and dictionaries there is no measurement showing a problem, so the reuse rule says to reuse.
- Keeping dictionary columns saved most of the Parquet decode cost for the string columns in the spike. A batch type that expands them would throw that away.
- The interface in front of the kernels is what makes "replace one at a time" and later fusion cheap.

## Alternatives considered

- **A. arrow-rs kernels everywhere.** Least work and the best reuse. Its `Decimal64` kernels are about as fast as its integer kernels. Lost on selection-aware errors (it would copy to compact before every strict kernel), on the 1.6-1.8x cost, and on `Decimal128`; we would also own a strictness layer anyway.
- **B. Our own kernels for everything from day one.** Maximum control. Lost: no evidence that comparisons, strings or filters need it, and it delays every slice.
- **C. A different batch layout (DuckDB-style flat, constant, dictionary vectors).** More encodings are possible. Lost: the vision fixes Arrow as the interop format and the Parquet reader produces Arrow, so a second layout means a conversion at every edge.
- **D. Floating point for decimals.** Fast and simple. Lost: results change with thread count and are not exact.

## Evidence

**Measured** (`bench/results/20261103-kernels-arrow-rs.md`, `bench/results/20261103-pipeline-model-spike.md`; x86-64 only, shared VM; kernels single thread, 8192-row batches, synthetic data, no selection vector):

- `p * (100 - d)`, ns/row: arrow checked `i64` 1.9-2.5; arrow `Decimal64` 1.9-2.2 (result type `Decimal64(18, 4)`); arrow `Decimal128` 4.5-9.6 (varies across builds of the same code, cause unknown); own two passes 1.2-1.3; own one fused pass 0.74-0.78; own narrowed to `i64` and building a `Decimal128(31,4)` array 1.3-1.4 (the output width an exact `p1 + p2` multiplication rule would have needed; the adopted rule keeps 64-bit operands at 64 bits, which is the 0.74-0.78 path); own `i128` loop 2.7-3.4. Allocating the output per batch cost nothing extra (0.74 against 0.75-0.78).
- With 10% NULLs: arrow 2.4-2.7, an own loop that branches on validity 3.1-3.5 (worse than arrow), a branch-free own loop 1.6-1.7.
- Semantics: plain `sum` wraps silently, default `cast` returns NULL, `*_wrapping` wraps; the checked variants error.
- In the Parquet spike: decoding the two string columns took 80-85 ms as plain strings and 13-14 ms as dictionary arrays; converting `i128` decimals to `f64` cost about 70 ms of a 100 ms project step; exact integer sums matched DuckDB digit for digit; filtering by copying cost about 40 ms, and about 21 ms once the strings were dictionaries.
- Strictness lints (`bench/results/20261103-lint-check.md`; arrow 60.1, clippy 1.99.1): function-level bans work, including through re-exports; `arithmetic_side_effects`, `cast_possible_truncation` and `cast_possible_wrap` flag plain `+`, `*` and truncating `as`; `overflow-checks = true` makes release `i32::MAX + 1` panic, while the Cargo default wraps silently. `CastOptions::default()` and a literal `safe: true` cannot be flagged, which is why both cast functions are banned instead.

Generic-operator experiment (`bench/results/20261104-generic-ops-x86.md`; x86-64 only, shared 8-vCPU VM; TPC-H SF1 `lineitem`, two query shapes, no joins; results identical to DuckDB and, with synthetic NULLs, to a scalar reference):

- Cost of generality against a hand-fused loop over the same batches, interleaved, 25 rounds, 1-8 threads. End to end (Parquet decode included): Q1 1.06-1.12x, Q6 0.89-0.94x (generic faster). Engine only (decoded batches in memory): Q1 1.20-1.51x, Q6 0.67-0.82x. Control arms (generic against generic) 1.00-1.07.
- The first version was 2.1x on Q1 engine-only. A profile put 71% in the aggregation sink; computing group id, count and the three sums in one pass instead of five cut it to 1.47x. The selection vector and the primitive kernels were not the expensive part.
- Against DuckDB (in-process timer, min of 15, not interleaved with ours): generic Q1 end to end 0.79-0.94 of DuckDB's time, Q6 0.81-1.15 (slower at 1-2 threads, faster at 4-8). DuckDB's number includes parsing and planning; treat as comparable, not a ranking. (A first DuckDB timing had dropped the fastest run instead of the first; corrected in the results file.)
- **ARM64 (Neoverse-N3, `bench/results/20261104-generic-ops-arm64.md`): the gap is larger on the unselective query.** Q1 1.20-1.29x end to end and 1.5-2.0x engine-only; Q6 0.85x end to end (faster than fused). The NULL penalty is 2.1-2.7x. The reason for the larger Q1 gap is unknown (not profiled). In-process DuckDB on the same VM took longer than the generic engine in every cell (0.64-0.87 of its time), not interleaved.
- **NULL handling costs 1.8-2.5x of the engine-only time at 10% NULLs** in four columns, with three validity representations tried (bit test, bytes expanded per batch, hybrid on selection density); none got below about 1.8x.
- Kernel tests: 10 unit tests; a mutation run on the final code of 15 breakages found one test gap (subtraction overflow masking), now closed.

Decimal64 at the client edge (`bench/results/20261104-decimal-clients.md`; delegated agent; x86-64 only; the orchestrator re-ran the Flight, JDBC and Postgres-wire probes and the numeric encoder check): pyarrow Flight (`do_get`, `do_put`, `get_schema`), ADBC Flight SQL (Go driver 1.13.0) and a Rust `arrow-flight` 60.1.0 server accept `Decimal64` and keep the type (30 of 30 probes); the **Flight SQL JDBC driver 19.0.0 rejects any result set whose schema has a `Decimal64` column** (`Library only supports 128-bit and 256-bit decimal values`, even `SELECT * FROM empty`), and returns exact `BigDecimal` after the server widens to `Decimal128`; psycopg3, asyncpg and pg8000 accept `numeric` from a toy Postgres-protocol server (4 of 4). The `numeric` binary encoder is byte-identical to real PostgreSQL 16.2's `numeric_send` on 54 boundary cases and 20,000 fuzz values, and all 6 mutants are caught.

Kani proofs of the generic-ops kernels (`bench/results/20261104-kani-kernels.md`; ARM64 VM with 64 GB; 62 of 62 harnesses verified, 0 failed): the arithmetic kernels raise an error exactly when a selected AND valid row overflows, never otherwise; filters, sums and grouped sums equal their specifications; std's 64-bit `overflowing_mul` is proved exact for all inputs. The proofs are mutation-checked: each of the 15 deliberate kernel breakages makes at least one harness fail (15 of 15, 0 survivors; a first run that counted 'no result' as a catch for 5 of them was corrected). Bounds: rows <= 4 (grouped sums <= 3, 2 groups), stub for the error message; the `div` kernels and the `crates/nata-kernels` copy are not covered.

**Kani proofs of the REAL `nata-kernels` crate** (`bench/results/20261104-kani-nata-kernels.md`; 105 harnesses against `crates/nata-kernels/src/kernels.rs` included by `#[path]`, never copied; 64 GB ARM64 Spot VM, Kani 0.68, CBMC 6.11): **100 of 105 harnesses proved** (one of them, `group_sums_masked` at 1 row, reports a cover gap by construction; the same family at 2-3 rows has all covers satisfied), covering the kernels `mul`, `sub_const_left`, `div` and `div_const_left` (the division logic with the primitive replaced by a stand-in, up to 4 rows), the guards `split_ne`, `filter_ne`, `merge_branches` and a `CASE WHEN x <> 0 THEN a / x` pipeline, `filter_range`, `sum` and grouped sums, and the primitives `checked_div` at 8, 16 and 64 bits (the 64-bit one in 882 s) and the 64-bit multiply. Covers are now recorded per harness and satisfied for the largest-row harness of every proved family. **5 harnesses are NOT proved:** the exact-division proofs with the real 64-bit divide (`div_exact` and `div_const_left_exact`, rows 1-2) and the 32-bit `checked_div` primitive timed out at 900 s; the two `div_const_left_exact` also timed out at 3600 s; the other three got no longer run. The composition argument for division (stand-in logic plus an exact primitive) is therefore reasoned, not checked, and its 32-bit step is the unproved one. **Mutation check: 18 of 18 in-scope mutants caught by these proofs, 0 survived**; 4 mutants of the arrow wrapper (`arrow_path.rs`) are outside these proofs and are covered by the crate's differential tests only. Trust points that remain: the overflow error text is a stub, `NullBuffer` is a stand-in, and the arrow wrappers are not covered by the proofs.

Kernel crate, lints and guarded expressions (`bench/results/20261104-kernel-lints-and-guards.md`; delegated agent, the orchestrator re-ran fmt, clippy, workspace tests, the lint fixtures, the DuckDB diff and the mutation script; x86-64, timings at load 5):

- Guarded expressions: checked `div`/`div_const_left`, `filter_ne`/`split_ne` and `merge_branches`; 81 guard runs match a row-by-row reference; arrow's `div` without compaction errors on a masked-out row, and after compaction or null-buffer folding it matches ours (the reason for the compaction rule). Against DuckDB 2.0.0: 81 of 81 identical (42 result sets, 39 errors), using `//`; DuckDB's `//` errors on zero and on `MIN // -1` like Nata. **Reasoned:** selection-aware error semantics (a SQL requirement, but the interaction with arrow kernels is argued from how they compute, not measured); the selection-vector design and its compaction cost; `Decimal64` for precision up to 18 (the kernel micro-benchmark shows `i64` storage is faster than `i128`, but end to end the reader returning `Decimal64` made no difference beyond noise, because Parquet decode dominated); client-edge widening (Postgres wire `NUMERIC` and Arrow Flight SQL client support for `Decimal64` was not checked); the 5% and 1.5x thresholds; and that `clippy` `disallowed-methods` can express every ban in decision 6.

**Not covered:**

- ARM64: the kernel benchmark ran once, on one quiet Neoverse-V2 VM (`bench/results/20261104-arm64-run2-benchmarks.md`); nothing else (selection-aware kernels, real data) did. By source inspection arrow-rs kernels have no architecture-specific code and no NEON path (they rely on LLVM autovectorization), so there is no fast path to lose, and no measurement of what LLVM produces there. The `parquet` crate has none either.
- ARM64 for the generic-operator experiment on the V2 core (only N3 was run), and a profile of why Q1 is further from the fused loop there. Joins, general group-by (the experiment grouped on at most 32 dictionary codes), plain strings, casts, expressions wider than two operations, real (not synthetic) NULL distributions, buffer pooling and spill. The micro-benchmark loops are lower bounds; the experiment's fused baseline had no NULL handling.

## Confidence

- **Arrow's strict and lenient behaviour: high.** Measured on the version in use.
- **Selection-aware errors as a requirement: medium-high.** Standard SQL, argued from how arrow computes.
- **Own arithmetic and aggregate kernels: medium.** The reason is semantics first and a measured speed gain second: owning the primitive kernels is 1.6-1.8x faster than arrow's two checked kernels on x86-64 and 1.4-1.5x on ARM64 (right at the 1.5x rule), and fusing adds 1.5-1.7x (x86-64) or 1.8-1.9x (ARM64). The speed figures are micro-benchmarks without selection vectors or real data.
- **Reuse arrow-rs for everything else: medium.** No evidence either way; it follows the reuse rule.
- **The lint and `overflow-checks`: high for the lints, medium for `overflow-checks`.** Lints: verified on a real crate with 73 failing fixtures and controls. `overflow-checks`: works, but must be workspace-wide and costs up to 2x on `sum`; its effect on the end-to-end numbers is unmeasured.
- **Selection vector design: medium.** Built and measured on two queries on x86-64: correct against DuckDB and a scalar reference, and it let the selective query beat the hand-fused loop. Also run on ARM64 (N3) with the same outcome. Not measured with joins or a general group-by.
- **Cost of generality (end to end 1.06-1.12x on an unselective query on x86-64, 1.20-1.29x on ARM64 N3, faster on a selective one on both): medium.** One data set, two queries, a simple group-by. It shrinks to 1.2-1.5x engine-only, so it grows if decode gets faster.
- **NULL handling cost (1.8-2.5x of engine time at 10% NULLs): medium, and the largest known cost.** Measured, but no representation tried removes it; the word-wise bitmap approach is untried.
- **`Decimal64` at the client edge: medium-high for Arrow-native clients, a known rejection for Java/JDBC, handled by widening to `Decimal128` at the Flight SQL edge.** Measured on x86-64, one small table, the listed client versions. Not verified: other Java clients and JDBC versions, ODBC, pgjdbc, pgx, ARM64, and the cost of widening per batch.
- Would change if: own kernels with selection and NULL handling lose their 1.5x on real data or on ARM64; the generic-operator experiment on ARM64 or with joins shows the cost of generality outweighs the gains (on x86-64 and ARM64 N3 it does not so far); or a newer arrow-rs ships selection-aware or faster checked kernels.

## Consequences

- We own a thin kernel layer, its strictness tests, and the lint configuration from slice 2.
- A branch-free NULL strategy is part of every own kernel's design. The naive version is a regression.
- Every arrow-rs wrapper that cannot take a selection compacts first; that copy is unmeasured and may be the first thing to replace.
- The decimal rules are written (`docs/decimal-rules.md`); the kernels implement them, and `check/queries/decimal*` are the tests. The rules keep `price * (1 - disc) * (1 + tax)` on `DECIMAL(15,2)` columns at `DECIMAL(18,6)`, so the checked `i64` path measured here applies; they make division exact decimal, which needs a wider accumulator for `AVG`.
- Parquet scans must be able to hand back dictionary arrays and the narrowest decimal type, which may need our own page decoding later (the `parquet` crate expands dictionaries for some types).
- When dictionary-aware operators arrive (T2) they need a cap on the product of key cardinalities, with a hash fallback above it.
- Sums stay exact: `i128` accumulators for decimals, overflow is an error.
- The client edge needs two small pieces: a `Decimal64 -> Decimal128` cast of result batches with a schema rewrite for Flight SQL (and the precision/scale field metadata), and a `numeric` encoder (text and binary) for the Postgres edge, tested against a real PostgreSQL with the mutants of `spikes/decimal-clients/verify_numeric.py`. The widening cost per batch is unmeasured.
- Aggregation is written as one pass per group-key set that updates count and all sums together, not one pass per aggregate (a third of generic Q1 time in the experiment).
- NULL handling needs its own design work before it can be called done: it roughly doubles engine time at 10% NULLs. Candidates: word-wise bitmap operations, specialising on NULL-free batches (already done: kernels have a no-NULL path), or computing under a validity mask and deferring the check.
