## 1. Goal

`nata sql -c "SELECT l_orderkey FROM 's3://example-bucket/lineitem.parquet' WHERE l_orderkey > 0 LIMIT 10"` and the same query over `gs://example-bucket/lineitem.parquet` return the same typed rows as the identical local file and DuckDB httpfs. Local MinIO exercises the S3 path with default query settings. Deliver bounded asynchronous range reads, CPU-pool Parquet decode, and a bounded footer cache shared by binding and execution. Preserve local scan behavior and ordered scan/LIMIT semantics.

Scope is explicit object URIs (and an internal ordered file-list interface); remote glob/LIST discovery, Azure/R2 certification, data/NVMe/result caches, writes, and Iceberg catalog/manifest logic are not supported here. Slice 12 receives a cancellable, identity-pinned range/metadata interface with scoped credentials, not a catalog implementation. ADR 0005 rule 8's write/conditional-put permissions are unchanged.

## 3. Decision rules (fixed before measuring)

**Frozen 2026-11-07 against the reference run** (`bench/results/20261107-object-store-reference.md`; DuckDB httpfs and the spike controls on a real GCS bucket, both CPU types, 2,296 timed runs per CPU, 0 wrong answers):
- Performance: ≤1.5x DuckDB in every cell where the spike wrapper already met it (18 of 22); the four other cells get their measured ceilings: `files100` meta 2.00x, `files100` sel 2.00x, `small1` full 1.75x, `mid10` proj 1.90x. "Matched spike policy" means the merged wrapper, with a 1.2x ceiling per cell. Warm cache hits make exactly 0 footer GETs.
- Scalability: at least 0.9x the spike wrapper's measured 1→8 worker speedup per cell (SF10 full 4.05x ARM64 / 3.99x x86-64).
- Resource bounds, reliability and fault tolerance: the ADR 0011 caps, retry numbers and the 1 s quiescence, unchanged.
- **Rule 1 is not passed yet.** Its remaining gates come before the skeleton is accepted: the S3 credential chain, `cargo deny` with the unsafe inventory, and a hostile-length probe of the library paths that read success bodies (credential JSON, LIST and multipart XML). MinIO was unavailable in the spike, so the skeleton runs S3 against MinIO or a fake endpoint and says which.

1. **Reuse first:** propose `object_store`, not a new HTTP/signing client (vision). It passes only if bounded streaming, conditional/versioned range reads, both auth chains, cancel and dependency checks work behind our wrapper. If not, stop and propose an alternative with a narrow reuse/custom bake-off; no automatic custom client. The spike compared policies using one client, not clients.
2. **Request policy:** start at ADR 0011's caps, merge only within its byte-waste allowance; unmerged parallel reads are the control. Keep optional prefetch/cross-row-group merging only if ≥1.2x faster outside twin spread on both CPUs in affected cells, no cell >1.05x slower outside noise, and all memory/byte caps pass (**provisional performance targets**). Otherwise default them off; do not increase caps to rescue throughput. CPU morsels remain whole row groups, even if requests combine ranges.
3. **Runtime:** ADR 0002's split runtime remains the production choice. Its required separate-Tokio-CPU-runtime comparison is still open: same CPU/I/O thread budgets, policy and bytes, both idle and saturated. A ≥1.2x latency/throughput gain outside noise on both CPUs with no fault/resource regression triggers an owner proposal, never an automatic runtime rewrite. These are target thresholds.
4. **Cache:** no stale/mixed-version result is acceptable. Unchanged objects avoid repeated footer GETs, including binder→execution; bypass over-cap entries, never relax admission. Admit a cache/default only after key/invalidation, retained-byte and eviction checks pass. No TTL substitute for identity validation.
5. **Fair freeze:** first record DuckDB and spike control results, noise, achievable scaling and resource envelope in `bench/results/YYYYMMDD-object-store-reference.md`; owner/parent freezes final per-cell targets and defaults before production Nata numbers, as card 0005 did. Record any changed provisional proposal and reason. Missing real S3/GCS/DuckDB arm is NOT MEASURED, not PASS; noise-overlapping improvements are unresolved. Later misses remain NOT MET; no retrospective threshold changes.

## 4. Baseline spike (only the still-open questions)

Existing [simulated](../../bench/results/20261104-object-store-scan.md) and [real GCS](../../bench/results/20261105-object-store-real.md) evidence settles the need for bounded parallelism and the potential of merging: 16 vs sequential was 2.3–13.5x faster on GCS. It does not settle production retry/hostile-body bounds, cache design, client superiority, real S3 or a real-bucket DuckDB baseline. Do not repeat that whole spike as an architecture search.

Planned narrow experiment: exercise the proposed wrapper on the reused client with hostile responses and version races; no-cache vs bounded cache; and the ADR 0002 separate CPU-runtime arm. A custom client bake-off is conditional on rule 1 failing, not routine work. Target time box: one engineering day, then report unresolved questions. Planned result: `bench/results/YYYYMMDD-object-store-baseline.md`; reference timings in the separate reference record above. Neither exists yet.

Walking skeleton, first runnable change: the example query with default settings over MinIO **and a real bucket**, native `gs://` smoke, local identical-file and DuckDB checks, small SF1 smoke against frozen references, bounded grants/cache, cancel/fault probes, and S3-response plus damaged-Parquet fuzzers at **nightly size on GCP from day one**. Include real default clients and thin versions of every closeout check. Fuzz transport responses before the third-party client and range/footer bytes before Parquet; a post-download byte fuzzer alone misses client header/body handling. Lengths are bounded before allocation, remote chunk readers retain `CountingRead::at_eof` behavior, and potentially looping operations have deadlines. If the library allocates from hostile lengths before our bound, rule 1 fails; `catch_unwind` is insufficient.

This document-only task runs none of this. Implementation briefs must name direct dependencies: `object_store` 0.14 is in the spike's lockfile, **not the root lockfile**; its addition needs explicit owner/parent authorization. Locked root crates may become direct dependencies at locked versions with `cargo deny` and unsafe inventory. Heavy fuzz/mutants/loom/sanitizers/benchmarks go through `orchestrate.sh` on suitably sized Spot VMs (§8), never this development VM. No cloud run is authorized by this draft.
